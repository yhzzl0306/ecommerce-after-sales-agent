## 四、30 秒项目介绍

我做的是一个基于 Dify 和 FastAPI 的电商售后智能体。Dify 负责工作流编排、售后规则知识库和用户对话，FastAPI 提供订单、物流和售后申请接口。项目重点不是简单问答，而是控制有副作用的售后创建操作：用户没有明确确认时不创建，已有处理中申请时不重复创建，特殊商品和待付款订单会被拦截，后端还会进行最终业务校验。目前已经完成 15 条业务场景测试和后端自动化测试。

## 五、1 分钟项目介绍

项目面向电商售后场景，主要解决用户查询订单、查询物流、咨询售后规则和提交售后申请的问题。

整体采用 Dify + FastAPI 架构。Dify 侧负责工作流、LLM 和 RAG 知识库，FastAPI 侧负责结构化业务工具。用户输入订单号和问题后，工作流分别调用订单和物流接口，再检索售后规则，最后由 LLM 生成咨询结果。

对于创建售后这种有副作用的操作，我设计了三层防线。第一层是 Prompt 约束模型，第二层是 Dify 条件分支，要求用户明确确认，第三层是 FastAPI 后端校验订单状态、商品类型、重复申请和幂等键。项目还增加了处理中售后查询接口，避免用户重复提交；针对订单不存在和订单号格式错误，增加了稳定 lookup 接口，避免 Dify 直接因为 404 中断。

目前已经完成 15 条 Dify 业务场景回归测试、lookup 接口测试和 pytest 自动化测试。

## 六、3 分钟项目介绍结构

### 1. 背景

电商售后中，查询订单和创建售后风险不同。查询可以自动化，但创建申请会改变业务状态，不能只依赖模型输出。

### 2. 架构

```text
用户 → Dify 工作流 → FastAPI 工具服务 → 内存仓储
```

Dify 负责智能流程，FastAPI 负责确定性业务规则。

### 3. 核心流程

```text
订单查询 → 物流查询 → RAG 规则检索 → LLM 判断
→ 用户确认 → 查询处理中申请 → 创建资格判断 → 创建售后
```

### 4. 安全设计

```text
Prompt + 工作流条件 + 后端校验
```

### 5. 测试结果

覆盖普通订单、特殊商品、待付款、重复申请、未确认、订单不存在、错误订单号和物流状态冲突等场景。

### 6. 当前限制

使用内存仓储，尚未接入真实 mall、数据库和生产鉴权。

## 七、高频面试问题

### 1. 为什么不能只依赖 Prompt？

Prompt 只能约束模型行为，不能作为最终业务安全边界。模型输出具有不确定性，而创建售后会产生副作用，因此需要工作流分支和后端校验共同保护。

### 2. 为什么要设置用户确认门槛？

用户说“能不能申请售后”通常只是咨询，不代表要执行申请。只有明确说“确认申请售后”等操作意图后，才能进入创建流程。

### 3. 如何防止重复售后？

创建前先查询订单是否有处理中申请。如果存在，直接返回原申请号；后端还会检查相同订单的处理中状态，并通过幂等键处理网络重试。

### 4. 幂等键有什么作用？

网络超时、网关重试或用户重复点击可能造成同一个业务请求多次到达。服务端保存幂等键和首次结果，重复请求直接返回首次结果，避免重复创建。

### 5. 为什么 `PENDING_REVIEW` 不代表退款完成？

它只表示售后申请已提交并等待人工审核，后续可能审核通过、拒绝或进入退款流程，不能直接推断退款已经完成。

### 6. 为什么 HTTP 409 会导致 Dify 节点失败？

Dify HTTP 节点通常把非 2xx 响应视为节点失败。对于预期业务拒绝，项目在调用创建接口前先做确定性资格判断；FastAPI 的 409 作为最终兜底。

### 7. 为什么需要代码节点解析 HTTP body？

HTTP 节点只暴露 body，内部 JSON 字段不一定自动展开。代码节点把字符串 JSON 转成对象，并输出布尔值 `has_active_application`，供条件分支使用。

### 8. RAG 在项目中解决什么问题？

售后规则经常变化，不适合全部写死在 Prompt 中。知识库用于检索规则，LLM 根据检索上下文回答；但最终业务校验仍由后端完成。

### 9. 为什么使用内存仓储？

第一阶段主要验证工具契约和业务流程，内存仓储可以降低部署复杂度。生产环境会替换成 MySQL、Redis 或 mall HTTP 客户端。

### 10. 如果改成生产环境，怎么保证幂等？

使用数据库唯一索引或 Redis 分布式锁，幂等记录保存请求状态和结果，并设置过期策略；多实例部署时要保证所有实例访问同一份幂等数据。

### 11. 如何处理订单不存在？

原始接口可以返回 404，但 Dify 会把非 2xx 当成节点失败。因此增加稳定 lookup 接口，统一返回 HTTP 200，并通过 `found`、`error_code` 和 `message` 表达业务结果。

### 12. 如何测试工作流？

按业务风险设计测试集，分别验证普通成功、重复申请、待付款、特殊商品、未确认、非法订单号和不存在订单等场景，重点观察创建售后节点是否被错误执行。

## 4. 本阶段遇到的问题与排查

### 问题：知识检索节点的查询变量显示为空

#### 现象

最初创建的“知识检索”节点在“设置变量值”下拉框中只有系统变量，没有 `user_question`，无法完成查询文本配置。

#### 根因

该节点当时没有上游连接。Dify 的变量选择器只展示当前节点可访问的上游变量；虽然“开始”节点存在 `user_question`，但未形成可达路径，所以变量列表为空。

#### 处理过程

1. 先确认开始节点确实存在 `order_no` 和 `user_question`；
2. 发现无上游边后，尝试直接配置原知识检索节点；
3. 变量选择器仍没有用户输入变量；
4. 从“开始”节点的添加节点入口重新创建了 `知识检索 2`；
5. 新节点自动形成 `开始 → 知识检索 2`；
6. 此时变量列表出现 `用户输入 / user_question`；
7. 绑定查询变量并重新选择 `电商售后规则库`，配置成功。

#### 结论

这是工作流数据流可达性问题，不是 FastAPI、知识库索引或 SSRF 问题。

#### 后续清理

画布上目前保留了一个早期未连通的“知识检索”节点和一个已经连通、配置正确的“知识检索 2”节点。后续完成联调后，应删除未使用节点或重命名节点，避免面试演示时产生歧义。删除工作流节点属于破坏性操作，执行前需要确认保留哪一个节点。

## 6. 面试八股总结

### 6.1 RAG 基本链路

RAG 通常包括：文档加载、清洗与切分、Embedding 或倒排索引、向量/关键词检索、Top-K 召回、可选重排序、上下文拼接、LLM 生成。

本项目使用 Dify 知识库完成索引和检索，FastAPI 工具负责实时业务事实，LLM 负责解释和组织答案。

### 6.2 为什么规则不直接写死在 Prompt

规则会变化，也可能需要按文档维护。放进知识库后可以独立更新、检索和审计；Prompt 只约束模型行为和信息来源，减少规则与提示词强耦合。

### 6.3 工具数据与知识库数据如何分工

- 工具数据：实时、结构化、与订单实例相关；
- 知识库数据：相对稳定、面向规则和政策；
- LLM：不能替代工具查询，也不能把知识库规则当成实时订单事实。

### 6.4 Top-K、chunk、reranking

- `chunk` 太大：噪声多，影响上下文窗口；
- `chunk` 太小：规则上下文可能被切断；
- `chunk overlap`：减少切分边界导致的信息丢失；
- `Top-K`：控制召回片段数量，过大增加噪声和 Token；
- `reranking`：对初召回结果二次排序，提升相关性，但会增加延迟和资源消耗。

本项目第一版保留默认召回参数，等评估集完成后再调优，避免凭感觉改参数。

### 6.5 如何防止幻觉

1. 在 Prompt 中声明事实来源；
2. 工具返回结构化 JSON；
3. 规则和事实分栏展示；
4. 缺数据时明确“不足”，而不是让模型猜；
5. 创建售后前增加用户确认；
6. 通过日志保存输入、工具结果和最终输出，便于复盘。

## 8. 状态更新：上下文变量与联合测试（2026-09-28）

### 8.1 为什么 Prompt 中没有 `知识检索 2 / result`

知识库检索结果不能只作为普通 Prompt 文本插入。正确配置分两步：

1. 在 LLM 节点的“上下文”字段中选择 `知识检索 2 / result`，类型为 `Array[Object]`；
2. 在 Prompt 中输入 `/`，选择特殊变量 `上下文`。

完成后，LLM 节点不再提示“要启用上下文功能，请在提示中填写上下文变量”。

### 8.2 实际联合测试

输入：

```json

  "order_no": "202609070001",
  "user_question": "订单已签收三天，商品有质量问题，能否退款？"
}
```

Dify Test Run 实际返回：

- 订单信息：订单号 `202609070001`、状态 `COMPLETED`、金额 `99.9`、商品类型 `NORMAL`；
- 物流信息：物流状态为已签收，并读取签收时间；
- 规则依据：命中“已签收 7 天内的质量问题”，同时识别普通商品不能仅凭规则自动确认退款；
- 售后判断：建议人工审核，不直接承诺退款，并要求用户明确确认后才创建售后申请。

因此，本阶段已经完成第一条“订单工具 + 物流工具 + 知识库上下文 + LLM 输出”闭环。售后申请创建、特殊商品/待付款评估以及旧节点清理仍待完成。

### 8.3 联合测试发现的字段映射问题

第一次联合测试中，LLM 将物流工具返回的 `status: SIGNED` 输出成了“物流状态：COMPLETED”，实际是把订单工具的 `status: COMPLETED` 混入物流信息。这个问题不是 RAG 召回失败，而是两个工具 JSON 存在同名字段导致的来源混淆。

修复要求：

- 订单状态只允许读取 `查询订单 / body.status`；
- 物流状态只允许读取 `查询物流 / body.status`；
- Prompt 中明确写出字段来源；
- 测试断言同时检查订单状态为 `COMPLETED`、物流状态为 `SIGNED`。

这类错误要记录下来，面试时可以说明“工具调用成功不等于答案正确，还要做字段来源约束和结果校验”。

## 9. 2026-09-30：字段来源修复与三类场景测试

### 9.1 发现并修复查询物流节点地址问题

重新运行普通商品测试时发现，Dify 的“查询物流”节点实际只请求了：

```text
http://host.docker.internal:8001/orders/{order_no}
```

而不是物流接口：

```text
http://host.docker.internal:8001/orders/{order_no}/logistics
```

因为订单详情接口本身返回 200，这个问题没有表现为 404，而是表现为“物流节点读到了订单 JSON”：物流状态被错误读成 `COMPLETED`，承运商和运单号显示为未返回。

处理方式：在查询物流节点的 URL 末尾保留 Dify 已插入的 `用户输入 / order_no` 变量，并追加静态路径 `/logistics`。修复后重新测试，物流工具返回并被 LLM 正确输出：

```json
{
  "status": "SIGNED",
  "carrier": "示例物流",
  "tracking_no": "SF1234567890"
}
```

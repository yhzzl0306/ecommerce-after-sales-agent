## 1. 本阶段完成情况

本阶段把“售后咨询”推进成了一个可执行但受保护的业务闭环：

```text
用户咨询
  -> 查询订单 / 查询物流 / RAG 售后规则
  -> LLM 判断资格与下一步
  -> 只有用户明确确认
  -> 创建售后申请 HTTP
  -> 申请结果 LLM
  -> Output 输出申请号和当前状态
```

已完成：

- FastAPI `POST /after-sales/applications`；
- 订单状态、特殊商品和重复申请的后端校验；
- 幂等键回放；
- Dify 条件分支：只有用户输入“确认申请售后”等明确确认语句时才允许执行副作用接口；
- Dify HTTP JSON 动态变量映射：订单号来自 `用户输入 / order_no`，幂等键使用 `sys.workflow_run_id`；
- 第二个 LLM 和第二个 Output 节点，将申请号合流到最终用户可见结果；
- `GET /orders/{order_no}/after-sales/active`，用于查询订单当前是否已有处理中售后申请。

工作流仍保持未发布，当前只使用 Test Run 验证。

## 3. 三类业务边界测试

| 订单 | 场景 | 实际结果 | 是否创建申请 |
|---|---|---|---|
| `202609070001` | 已完成普通商品 + 明确确认 | HTTP `201`，创建 `PENDING_REVIEW` | 是 |
| `202609070002` | 已完成特殊定制商品 + 明确确认 | HTTP `409`，提示转人工审核 | 否 |
| `202609070003` | 待付款订单 + 明确确认 | HTTP `409`，只有已完成订单才能提交售后申请 | 否 |

重复对 `202609070001` 发起相同申请时，当前内存服务会返回“已有处理中售后申请”的 `409`；如果使用同一个幂等键重试，则会返回第一次申请结果并带 `X-Idempotent-Replay: true`。这两种行为分别覆盖了“重复业务申请”和“网络重试”两类问题。

## 4. 面试八股：为什么需要三层防线

1. **Prompt 层**：告诉模型哪些商品和状态不能直接承诺退款；
2. **工作流层**：用条件分支阻止未确认用户触发 HTTP 节点；
3. **服务端层**：最终在 FastAPI 再校验订单状态、商品类型和已有申请。

不能只依赖 Prompt，因为模型输出是概率性的，而创建售后申请属于有副作用的操作。后端必须把业务不变量作为最终边界。

## 5. 幂等设计

网络超时、客户端重试、网关重试或用户重复点击，都可能让同一个业务请求到达服务端多次。当前实现使用 `idempotency_key -> application` 映射：

- 首次请求创建申请并保存幂等键；
- 相同幂等键再次请求，直接返回原申请；
- 响应头 `X-Idempotent-Replay: true` 表示这是幂等回放；
- 幂等键如果绑定了不同订单或售后类型，返回 `409`，防止串单。

当前仓储是进程内存，适合演示和本地联调；生产环境应替换成数据库唯一索引或 Redis，并处理并发竞争、过期时间和多实例一致性。

## 10. 2026-10-09：重复申请查询分支联调成功

### 问题

HTTP 查询节点的 `body` 虽然包含 `has_active_application: true`，但 Dify 条件分支不能直接展开 JSON 内部字段，只能看到 `body`、`status_code`、`headers` 和 `files`。

### 处理

在“查询处理中售后申请”和“条件分支 2”之间增加代码节点“解析处理中申请结果”：

1. 读取 HTTP 节点 `body`；
2. 使用 JSON 解析得到对象；
3. 将 `has_active_application` 转换为布尔输出；
4. 将申请号、状态和完整 JSON 作为后续节点变量输出。

条件分支改为：

```text
解析处理中申请结果 / has_active_application == true
```

### 实际结果

测试订单：`202609070001`

执行路径：

```text
查询处理中售后申请
  -> 解析处理中申请结果
  -> 条件分支 2：IF
  -> 已有申请结果 LLM
  -> Output
```

创建售后申请节点未执行，最终用户看到：

```text
申请号：ASA199F40A7B8B
订单号：202609070001
售后类型：QUALITY_REFUND
当前状态：PENDING_REVIEW（待人工审核）
```

说明重复申请保护链路已经完成：已有处理中申请时，系统会直接返回原申请信息，不再调用 POST 创建接口。

### 面试要点

HTTP 节点的 JSON 响应不一定会自动映射为工作流变量。对于需要参与条件判断的字段，应增加数据转换节点，明确输出布尔值、字符串或结构化对象，避免把字符串 `"true"` 和布尔值 `true` 混淆。

## 11. 2026-10-09：业务拦截输出与确认分支收敛成功

本轮修复了两个问题：

1. HTTP `409` 业务冲突不再直接暴露为工作流错误；
2. 原始咨询 Output 不再与确认后的业务结果同时输出。

调整后的流程：

```text
用户确认判断
  ├─ 未确认 -> 原咨询 Output
  └─ 已确认 -> 查询处理中申请
                  ├─ 已有申请 -> 返回已有申请结果
                  └─ 没有申请 -> 判断创建资格
                                  ├─ 不允许 -> 直接输出业务拦截原因
                                  └─ 允许 -> 创建售后申请
```

订单 `202609070002` 的正确业务结论为：

```text
特殊定制商品需要转人工审核，不能自动创建售后申请。
```

订单 `202609070003` 的正确业务结论为：

```text
当前订单尚未完成，只有已完成订单才能提交售后申请。
```

两个场景均未执行创建售后申请节点，避免把预期的业务拦截显示成 `Request failed with status code 409`。

同时，将原来的 `LLM -> Output(text)` 改为“未确认”分支专属输出，避免确认场景把原始咨询内容和最终业务结果拼接在一起。

### 面试要点

预期业务拒绝不应完全依赖异常路径。工作流可在副作用接口之前完成确定性资格判断，向用户返回稳定的业务提示；服务端 `409` 仍保留为最终兜底，防止绕过工作流的非法调用。

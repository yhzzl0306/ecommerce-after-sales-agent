3. 遇到的问题

知识检索节点的查询变量为空

初始节点没有上游连接，Dify 变量选择器只显示系统变量，看不到 user_question。根因是工作流变量的可达性，而不是 FastAPI、索引或 SSRF 问题。

  1. 确认开始节点存在 order_no 和 user_question；
  2. 确认知识检索节点没有上游边；
  3. 从开始节点入口重新创建“知识检索 2”；
  4. 新节点形成 开始 → 知识检索 2 后，变量列表出现用户输入变量；
  5. 绑定变量并选择知识库，配置成功。

画布目前保留了一个早期未连通节点和一个正确配置的“知识检索 2”。完成联调后应清理未使用节点；删除前需要确认保留节点。

6. 面试八股

  • RAG 链路：加载、清洗切分、索引/Embedding、召回、Top-K、重排、上下文拼接、生成。
  • 工具负责实时订单事实，知识库负责售后规则，LLM 负责解释，不混淆信息来源。
  • chunk 太大噪声高，太小可能切断规则；overlap 用于降低边界损失。
  • Top-K 太大增加噪声和 Token；reranking 提升相关性但增加延迟。
  • 通过来源约束、结构化 JSON、缺数据兜底、用户确认和日志复盘降低幻觉与误操作。

7. 面试表述

我先用 FastAPI 实现订单和物流工具，再在 Dify 中导入售后规则知识库。联调时发现没有上游连接的知识检索节点无法看到用户问题变量，定位为工作流变量可达性问题，改为从开始节点建立检索分支后解决。目前正在把检索结果接入 LLM，并用三类订单做联合判断测试。

8. 状态更新：上下文变量与联合测试（2026-09-28）

知识库检索结果不能只作为普通 Prompt 文本插入。正确配置是：先在 LLM 的“上下文”字段选择 知识检索 2 / result，再在 Prompt 中输入 / 并选择特殊变量 上下文。

{
  "order_no": "202609070001",
  "user_question": "订单已签收三天，商品有质量问题，能否退款？"
}

Dify Test Run 实际返回了订单信息、物流信息、规则依据和售后判断四部分，命中“已签收 7 天内的质量问题”规则，并建议人工审核，不直接承诺退款。

9. 2026-09-30：字段来源修复与三类场景测试

真实问题：Dify 的“查询物流”节点曾只请求 /orders/{order_no}，因此返回了订单 JSON。由于该接口返回 200，问题不是 404，而是物流字段来源错误。

修复：保留 Dify 变量 用户输入 / order_no，在末尾追加 /logistics。修复后实际读到 status=SIGNED、承运商“示例物流”和运单号 SF1234567890。

9.1 普通商品

{
  "order_no": "202609070001",
  "user_question": "订单已签收三天，商品有质量问题，能否退款？"
}
  • 订单状态：COMPLETED；物流状态：SIGNED（已签收）；承运商和运单号读取正确。
  • 命中“已签收 7 天内的质量问题”，但因缺少凭证、当前日期和平台政策，未直接承诺退款。
  • 未创建售后申请。

9.2 特殊定制商品

{
  "order_no": "202609070002",
  "user_question": "这个定制商品有质量问题，可以退款吗？"
}
  • 识别商品类型 SPECIAL、物流状态 SIGNED。
  • 命中特殊商品规则；要求质量凭证和平台政策确认，建议转人工。
  • 未创建售后申请。

9.3 待付款订单

{
  "order_no": "202609070003",
  "user_question": "这个订单可以申请退款吗？"
}
  • 识别订单状态 PENDING_PAYMENT、物流状态 NOT_SHIPPED、售后状态 NONE。
  • 模型没有在规则不完整时直接承诺退款，要求先确认是否已支付，并说明创建申请不等于退款完成。
  • 未创建售后申请。
